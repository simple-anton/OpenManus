## Находки

### [APPSEC-01] CSRF через `Origin: null`: сторонняя страница пишет произвольную команду в `mcp.json` и подменяет адрес провайдера
Роль: APPSEC | Серьёзность: Критическая | Уверенность: подтверждено экспериментом
Где: `app/web/server.py:70-89` (`_guard_request`, условие `value and value != "null"`), `:249-261` (middleware), `POST /api/mcp` (`:344-353`), `POST /api/settings` (`:495-505`), `POST /api/settings/test` (`:539-556`)
Простыми словами: пока контейнер работает, достаточно открыть в обычном браузере вредную страницу — и она может тайно перенастроить вашего агента: прописать команду, которая выполнится в контейнере, или подменить адрес, куда уходит ваш ключ.
Суть: middleware `guard` блокирует кросс-сайт по `Origin`/`Host`, но намеренно пропускает `Origin: null` (условие `value != "null"`) и запросы вовсе без `Origin`/`Referer`. `Origin: null` шлёт браузер из iframe с атрибутом `sandbox` и из `data:`-документа. Аутентификации у API нет вовсе.
Сценарий:
1. Владелец с работающим контейнером открывает страницу противника.
2. Страница: `<iframe sandbox srcdoc="<script>fetch('http://localhost:8000/api/mcp',{method:'POST',body:JSON.stringify({servers:{x:{type:'stdio',command:'/bin/sh',args:['-c','…']}},disabled:{}})})</script>">`. Тело без `Content-Type` FastAPI разбирает как JSON.
3. `mcp.json` перезаписан; при следующем запуске агента команда стартует в контейнере от root. Либо через `/api/settings` подменён `llm.base_url`, а `/api/settings/test` тут же отправляет `Authorization: Bearer <ключ>` на адрес противника.
Доказательство: эксперимент C на настоящем `create_app()`: запрос с `Origin: null` без `Content-Type` достиг обоих обработчиков (200), `mcp.json` записан с командой `/bin/sh`, `llm.default.base_url` стал `https://attacker.example/v1`. Кросс-сайт с `Origin: https://evil.com` корректно отклонён (403).
Последствия: удалённое (через браузер владельца) выполнение кода в контейнере и кража ключа API. `mcp.json` и `config.toml` — тома, вред переживает пересборку.
Исправление: (1) в `_guard_request` трактовать `Origin: null` как запрет для всех мутирующих эндпоинтов (убрать `and value != "null"`), а запросы без `Origin`/`Referer` к POST/PUT/DELETE — отклонять; (2) добавить простую аутентификацию (токен в куке `SameSite=Strict`/локальный секрет), не полагаясь только на заголовки; (3) требовать `Content-Type: application/json` и заголовок вроде `X-Requested-By`.
Как проверить: тест с `TestClient` — `Origin: null` + без `Content-Type` к `/api/mcp` должен давать 403.

### [APPSEC-02] Песочница не подключена к исполнению кода и не заработает в этой развёртке
Роль: APPSEC | Серьёзность: Критическая | Уверенность: подтверждено чтением кода
Где: `app/tool/python_execute.py` (нет обращения к песочнице), `app/tool/str_replace_editor.py:105-110` (единственное чтение `use_sandbox`), `app/sandbox/core/sandbox.py:45` (`docker.from_env()`), `docker-compose.yml` (docker-сокет не проброшен)
Простыми словами: «песочница, которую можно включить» на самом деле не охватывает главное — выполнение кода. А если её включить тумблером, она попытается создать ещё один контейнер через Docker, которого изнутри нет, и просто сломает работу с файлами.
Суть: `config.sandbox.use_sandbox` читается только при выборе файлового оператора в `str_replace_editor`. `python_execute` всегда исполняет код локально в контейнере (`multiprocessing.Process`). `app/sandbox/*` требует `docker.from_env()` — доступа к docker-сокету, который в контейнер не проброшен (и правильно, что не проброшен). То есть обещанной в справке «песочницы по умолчанию выключенной, но существующей» для кода нет.
Сценарий: владелец, прочитав справку/аудит, включает песочницу в настройках ради безопасности → `python_execute` как исполнял код рядом с ключами, так и исполняет; `str_replace_editor` пытается уйти в несуществующий Docker и падает.
Доказательство: `use_sandbox` в коде встречается только в `str_replace_editor.py` и `settings.py`; `python_execute.py` его не упоминает. `sandbox.py:45` — `self.client = docker.from_env()`.
Последствия: ложное чувство защиты; включение тумблера ухудшает работу, не добавляя изоляции.
Исправление (промежуточные варианты, от дешёвого к надёжному):
- **Минимум:** исполнять `python_execute` в отдельном контейнере-исполнителе (docker compose service), примонтировав туда ТОЛЬКО `workspace/`, без `config` и `browser-profile`, без ключей в окружении, с `network_mode: none` по умолчанию.
- **Средне:** тот же исполнитель + сеть по белому списку (прокси, разрешающий только домены задачи) — сохраняет запасной путь добычи.
- **Дёшево частично:** оставив локальное исполнение, запускать процесс-исполнитель от отдельного пользователя (не root) и `os.environ` без ключей + отзыв прав на чтение `config`/`browser-profile` через права ФС.
Цена для владельца-непрограммиста: один раз пересобрать образ по кнопке; поведение то же, кроме того, что код больше не видит ключи.
Как проверить: из `python_execute` попытаться `open('/app/OpenManus/config/config.toml')` — должно падать «нет файла/доступа».

### [APPSEC-03] Дочерний процесс кода переживает таймаут; лимиты обходятся
Роль: APPSEC | Серьёзность: Высокая | Уверенность: подтверждено экспериментом
Где: `app/tool/python_execute.py:125-133` (`proc.terminate()`), `:30-45` (`RLIMIT_AS`, `RLIMIT_FSIZE`)
Простыми словами: код агента может запустить фоновый процесс, который продолжит работать даже после того, как основной код «остановлен по таймауту». Ограничение на память и размер файла тоже обходятся.
Суть: `proc.terminate()` шлёт SIGTERM только процессу-исполнителю; дочерние (Popen) осиротевают и продолжают. `RLIMIT_FSIZE` ограничивает один файл — можно писать много файлов; `RLIMIT_AS` не ограничивает число процессов (нет `RLIMIT_NPROC`), fork-бомба возможна.
Сценарий: инъекция → код `subprocess.Popen([...])` с длительной задачей (майнер, туннель, эксфильтрация порциями) + основной код завершается → фоновый процесс живёт до перезапуска контейнера.
Доказательство: эксперимент P2 — дочерний процесс записал файл через 3 с после того, как родитель убит по таймауту 2 с.
Последствия: обход таймаута как «предохранителя»; фоновая активность вне видимости.
Исправление: запускать код в новой группе процессов (`start_new_session=True` / `os.setsid`) и убивать всю группу (`os.killpg`); добавить `RLIMIT_NPROC`; ограничить диск квотой каталога, а не размером файла. Радикально — контейнер-исполнитель (APPSEC-02), где убивается весь контейнер.
Как проверить: повторить эксперимент P2 после правки — файл не должен появиться.

### [APPSEC-04] noVNC на 6080 без пароля; риск доступа к сессиям владельца
Роль: APPSEC | Серьёзность: Высокая | Уверенность: подтверждено чтением кода (Origin-проверка websockify — гипотеза)
Где: `scripts/docker-entrypoint.sh:126` (`x11vnc … -nopw -localhost`), `:135` (`websockify … 6080 127.0.0.1:5900`), `docker-compose.yml:12`
Простыми словами: «живое окно» браузера контейнера открыто без пароля. Оно защищено только тем, что порт виден лишь с вашего компьютера. Если у веб-страницы получится к нему подключиться, она получит браузер с вашими входами на сайты.
Суть: единственная защита порта 6080 — привязка к 127.0.0.1. WebSocket не подчиняется правилам CORS, и если `websockify` не проверяет заголовок `Origin`, вредная страница в браузере владельца может открыть `ws://127.0.0.1:6080/...` и управлять VNC. Требует проверки версии websockify.
Сценарий: владелец открывает вредную страницу → та подключается по WebSocket к noVNC → действия в браузере контейнера от имени владельца (где он входил в банк/почту).
Доказательство: `-nopw` в entrypoint; проверка Origin в websockify по умолчанию отсутствовала в старых версиях. Версия в образе — из пакета Debian, конкретику не проверял (нет запуска).
Последствия: захват аутентифицированных сессий владельца через браузер.
Исправление: включить пароль VNC (сгенерировать при старте, показать владельцу) либо поставить перед noVNC прокси с проверкой `Origin`/`Host` и токеном; не полагаться только на 127.0.0.1.
Как проверить: со стороннего Origin открыть WebSocket к 6080 — должно отклоняться; проверить версию websockify на наличие `--verify-client`/встроенной проверки Origin.

### [APPSEC-05] SSRF и утечка ключа через тест-эндпоинты
Роль: APPSEC | Серьёзность: Высокая | Уверенность: подтверждено чтением кода
Где: `app/web/api_tools.py:47-118` (`try_call` — любой URL, любые заголовки, все методы), `app/web/server.py:539-556` (`/api/settings/test` шлёт `Bearer <api_key>` на `llm.base_url`), `app/web/server.py:510-523` (`/api/settings/models`)
Простыми словами: два служебных эндпоинта можно заставить сходить на любой адрес — в том числе на внутренние сервисы вашего Mac — и один из них при этом отправляет ваш ключ на указанный адрес.
Суть: `api_tools.try_call` не ограничивает схему/адрес (SSRF на `host.docker.internal`, метаданные, `file://`? — проверить схему httpx). `/api/settings/test` отправляет ключ на текущий `base_url` — в связке с APPSEC-01 (подмена `base_url`) это прямая эксфильтрация ключа.
Сценарий: см. APPSEC-01, шаг с `settings/test`; либо через `api-tools/test` — запрос к `http://host.docker.internal:<порт>` для разведки сервисов Mac.
Доказательство: код `try_call` строит запрос из `spec` без валидации хоста; `/api/settings/test` берёт `llm.api_key` в заголовок.
Последствия: SSRF во внутреннюю сеть Mac; эксфильтрация ключа в связке с CSRF.
Исправление: запретить в `api_tools`/`fetch` приватные диапазоны и `file://`/`gopher://` (блок-лист `127/8`, `10/8`, `172.16/12`, `192.168/16`, `169.254/16`, `host.docker.internal`), если явно не разрешено; `/api/settings/test` — не слать ключ на неподтверждённый новый `base_url`.
Как проверить: `try_call` с `url=http://169.254.169.254/...` и `file:///etc/passwd` — должно отклоняться.

### [APPSEC-06] Цепочка поставок: MCP-серверы и browser-use скачиваются во время работы через `uvx`/`npx -y`
Роль: APPSEC | Серьёзность: Средняя | Уверенность: подтверждено чтением кода
Где: `app/agent/manus.py:23-24` (`uvx browser-use --cli-mcp`), `app/web/settings.py:160-258` (каталог MCP: `uvx`, `npx -y ...` без пинов версий)
Простыми словами: часть компонентов не входит в образ, а докачивается из интернета при запуске, всегда свежая версия. Подмена или взлом такого пакета сразу попадает в вашу систему.
Суть: `uvx browser-use`, `npx -y @modelcontextprotocol/...` тянут последние версии на лету, без фиксации и без проверки хэшей. `browser-use` управляет браузером с сессиями владельца.
Последствия: компрометация через обновление зависимости; недетерминируемость сборки.
Исправление: пинить версии; предпочесть установку в образ на этапе сборки; для критичного `browser-use` — фиксированная версия и хэш.
Как проверить: зафиксировать версии, пересобрать, убедиться, что при работе ничего не докачивается.

### [APPSEC-07] `host.docker.internal` открывает сервисы Mac владельца коду агента
Роль: APPSEC | Серьёзность: Средняя | Уверенность: гипотеза (проверяется на машине владельца)
Где: `docker-compose.yml:31-33`
Простыми словами: из контейнера виден ваш компьютер по адресу `host.docker.internal`. Что именно там доступно, зависит от того, какие программы у вас слушают сеть.
Суть: `extra_hosts: host.docker.internal:host-gateway` даёт коду агента (и SSRF из APPSEC-05) доступ к любым портам, слушающим на Mac (Ollama, БД разработчика, панель Docker, локальные веб-приложения). На Mac непрограммиста поверхность мала, на Mac разработчика — велика.
Последствия: разведка и доступ к локальным сервисам Mac.
Исправление: оставлять `host.docker.internal` только если реально используется локальная модель; иначе убрать. При использовании — только конкретный порт через прокси.
Как проверить (на машине владельца): из `python_execute` просканировать типовые порты `host.docker.internal` — увидеть, что отвечает.

### [APPSEC-08] Мелкий XSS в интерфейсе через `base_url` (model-meta)
Роль: APPSEC | Серьёзность: Низкая | Уверенность: подтверждено чтением кода
Где: `app/web/static/index.html:2851` (`innerHTML = "<b>"+llm.model+"</b><br />"+llm.base_url`)
Простыми словами: адрес провайдера вставляется в страницу без экранирования. Сам по себе он ваш, но в связке с подменой настроек (APPSEC-01) туда можно записать вредную разметку.
Суть: `base_url`/`model` из конфигурации попадают в `innerHTML` без `escapeHtml`. Отчёт (`markdown()`) экранируется корректно — там XSS нет (проверено экспериментом D).
Последствия: XSS в интерфейсе владельца в связке с CSRF-подменой `base_url`.
Исправление: экранировать `model`/`base_url` перед вставкой (`textContent` или `escapeHtml`).
Как проверить: задать `base_url="<img src=x onerror=alert(1)>"`, открыть настройки — скрипт не должен исполниться.

## Требует разрешения
- Запуск `pip-audit` (уязвимости зависимостей), `semgrep` (шаблоны), `gitleaks` (история). Дали бы систематическую проверку цепочки поставок и подтверждение отсутствия секретов. Нужна установка инструментов (сеть). Стоимость — только трафик.

## Вне зоны
- `python_execute` с полными builtins/root (роль 01, AI-SEC-01) — периметр самого исполнения кода.
- Отсутствие бюджета токенов (роль 08) — CSRF-запуск задач усиливает риск трат.
