# Роль 03. Устойчивость добычи данных

Проверял: аудитор. Угол: насколько полно и надёжно агент достаёт данные, когда источник сопротивляется. Продукт — универсальный, любая страна/язык.

## Что проверено

| Область | Статус |
|---|---|
| Кодировка (charset только в `<meta>`) | подтверждено экспериментом (мусор) |
| Сканированный PDF без текстового слоя | подтверждено экспериментом (пусто, без OCR) |
| Коллизии имён сохранённых файлов | подтверждено экспериментом (перезапись) |
| CSV с `;` и запятой | подтверждено экспериментом (работает) |
| Определение JS-каркаса (пороги) | проверено чтением кода |
| Пагинация / бесконечная прокрутка / «показать ещё» | проверено чтением кода (нет) |
| Таймауты и ретраи | проверено чтением кода |
| `.doc`/`.docx`/`.xls`/архивы | проверено чтением кода |
| `MAX_BYTES` без Range | проверено чтением кода |
| robots / rate limit | проверено чтением кода (не обрабатываются) |

## Находки

### [EXTRACT-01] Кодировка берётся только из HTTP-заголовка: страницы с charset в `<meta>` превращаются в мусор
Роль: EXTRACT | Серьёзность: Высокая | Уверенность: подтверждено экспериментом
Где: `app/tool/http_fetch.py:126-133` (`_from_html`: `raw.decode(encoding or "utf-8","replace")`, затем bs4 получает уже строку), `:441` (`response.encoding`)
Простыми словами: если сайт указал свою кодировку не в заголовке ответа, а внутри HTML (как делают многие госсайты и старые порталы), агент прочитает текст как нечитаемую «кракозябру» и решит, что на странице ничего нет.
Суть: `httpx` даёт `encoding` из HTTP-заголовка `Content-Type`; если его там нет — `None`, и `_from_html` декодирует как utf-8 с `errors="replace"`, передавая BeautifulSoup уже декодированную строку. Тем самым штатное определение кодировки bs4 по `<meta charset>`/BOM выключено.
Сценарий: портал статистики в windows-1251 (или gbk/shift_jis/iso-8859-2) без charset в заголовке → агент видит `����� ...`, числа-цифры уцелевают, но подписи к ним — мусор → источник выглядит пустым/нечитаемым, агент уходит.
Доказательство: эксперимент E1 на реальном `_from_html`: страница windows-1251 → `'���� �����\n������� ����: 785000 ...'`.
Последствия: систематический недобор с целых классов сайтов (кириллица cp1251, восточноазиатские кодировки, RTL) → смещение выборки в сторону современных utf-8 сайтов.
Исправление: не декодировать вручную. Передавать BeautifulSoup сырые байты (`BeautifulSoup(raw, "html.parser", from_encoding=...)`) и дать ему определить кодировку по `<meta>`/BOM; либо использовать `response.text` httpx только когда charset в заголовке есть, иначе — детекция (charset-normalizer уже в зависимостях httpx).
Как проверить: тест `_from_html` на фикстурах cp1251/gbk/shift_jis без charset в заголовке — текст должен читаться.

### [EXTRACT-02] Сканированный PDF отдаёт пустоту без OCR и без предупреждения
Роль: EXTRACT | Серьёзность: Высокая | Уверенность: подтверждено экспериментом
Где: `app/tool/http_fetch.py:172-186` (`_from_pdf` через pypdf)
Простыми словами: PDF, который на самом деле картинка-скан (частый формат официальных публикаций), агент «прочитает» как пустой — и запишет источник как обработанный, хотя не извлёк ни цифры.
Суть: `pypdf.extract_text()` для страниц без текстового слоя возвращает пустую строку; OCR нет. `_from_pdf` вернёт только заголовки `--- страница N ---` без содержимого. Признака «текста нет» наверх не передаётся.
Сценарий: годовой отчёт ЦБ/статведомства выложен сканом → `fetch` сохраняет PDF, возвращает пустые страницы → агент считает документ прочитанным, факты из него не попадают в журнал → тихая потеря ключевого первоисточника.
Доказательство: эксперимент E2 — PDF-страница без текста дала только `--- страница 1 ---`.
Последствия: первоисточники-сканы систематически выпадают; хуже пробела — выглядит как «прочитано».
Исправление: если суммарный извлечённый текст пуст/крайне мал при N страниц — вернуть явное «PDF без текстового слоя (скан): нужен OCR, данные не извлечены» и пометить источник как непрочитанный; опционально подключить OCR (tesseract) как отдельный, ресурсоёмкий путь.
Как проверить: тест `_from_pdf` на скане — результат должен содержать явное предупреждение, а не пустые заголовки.

### [EXTRACT-03] Коллизия имён: второй `fetch` страницы того же сайта затирает файл первой
Роль: EXTRACT | Серьёзность: Высокая | Уверенность: подтверждено экспериментом
Где: `app/tool/http_fetch.py:265-284` (`_text_name`: только host+path, query отбрасывается), `:526-536` (`_save_text` пишет по этому имени)
Простыми словами: если данные на сайте различаются только «хвостом» адреса (страница 1, 2, 3 одного раздела), агент сохранит их все в один файл, и каждая следующая страница затрёт предыдущую. Собранное молча теряется.
Суть: `_text_name` строит имя из `netloc+path`, отбрасывая query. Для сайтов с `?id=…`/`?page=…` (типично для порталов статистики и каталогов) разные страницы дают одно имя → перезапись.
Сценарий: агент читает `?id=01`, `?id=02`, `?id=03` одного раздела → на диске один `armstat.am_ru.txt` с последней страницей; при вытеснении из памяти ранние данные не восстановить (файла с ними уже нет).
Доказательство: эксперимент E3 — оба `?id=01` и `?id=02` дали `armstat.am_ru.txt`.
Последствия: тихая потеря добытого именно на многостраничных источниках данных — самом ценном классе.
Исправление: включать в имя короткий хэш полного URL (включая query); либо не отбрасывать query при построении имени.
Как проверить: тест — два URL, различающихся только query, дают разные имена файлов.

### [EXTRACT-04] Нет пагинации, «показать ещё» и бесконечной прокрутки
Роль: EXTRACT | Серьёзность: Высокая | Уверенность: подтверждено чтением кода
Где: `app/tool/http_fetch.py` (`Fetch`, `Crawl` идут только по `<a href>` того же хоста), нет обработки `rel=next`/`?page=`
Простыми словами: если данные разбиты на страницы кнопками или подгружаются при прокрутке, агент увидит только первую порцию.
Суть: `crawl` следует лишь `<a href>`; пагинация через JS-кнопки, `rel="next"`, `?page=N`, «load more» (XHR) не распознаётся. Только `browser_exec` вручную, что медленно и требует инициативы модели.
Сценарий: каталог объявлений/реестр сделок на 50 страниц → агент берёт первую, выводы строит на 2% данных.
Последствия: систематический недобор на любых листинговых источниках; смещение к «первой странице».
Исправление: распознавать `rel="next"` и типовые `?page=`/`?offset=` в ссылках и предлагать их в очередь `crawl`; в промпте — правило про пагинацию.
Как проверить: фикстура с `rel=next` — проверить, что следующая страница попадает в очередь.

### [EXTRACT-05] Таймаут 25 с без ретраев — тяжёлый портал отпадает молча
Роль: EXTRACT | Серьёзность: Средняя | Уверенность: подтверждено чтением кода
Где: `app/tool/http_fetch.py:42` (`TIMEOUT=25.0`), `_one` (нет ретраев), `:756` (`CRAWL_BUDGET=120`)
Простыми словами: медленный государственный портал, которому нужно больше 25 секунд, агент сочтёт недоступным с первой попытки.
Суть: один запрос, `TimeoutException`→строка «сервер не ответил», без экспоненциального повтора. Для перегруженных госпорталов 25 с мало.
Последствия: недобор с медленных, но ценных официальных источников.
Исправление: 1-2 ретрая с backoff на таймаут/5xx; для крупных документов — увеличенный таймаут.
Как проверить: MockTransport с задержкой — убедиться в ретрае.

### [EXTRACT-06] `.doc`/`.docx`/`.xls`/архивы не извлекаются автоматически
Роль: EXTRACT | Серьёзность: Средняя | Уверенность: подтверждено чтением кода
Где: `app/tool/http_fetch.py:248-262` (`_extension` знает форматы), `:588-618` (`_render` не разбирает doc/docx/zip), `_from_xlsx` (openpyxl не читает старый `.xls`)
Простыми словами: документы Word, старый Excel и архивы агент сохранит, но не прочитает сам — рассчитано, что модель догадается распаковать их кодом. Слабая модель часто не догадается.
Суть: `_render` для doc/docx/zip возвращает «двоичные данные — читайте через python_execute»; `.xls` openpyxl не поддерживает. Извлечение переложено на инициативу модели (`subprocess unzip`, конвертеры).
Последствия: потеря данных из распространённых форматов госвыгрузок.
Исправление: авто-извлечение `.docx` (python-docx), `.xls` (xlrd), листинг `.zip` с авто-разбором вложенных таблиц; или явная инструкция + пример в ответе `fetch`.
Как проверить: `_render` на .docx/.zip — должен давать текст/список, а не «двоичные данные».

### [EXTRACT-07] `MAX_BYTES=40МБ`: большой файл не читается вовсе, без Range/частичного чтения
Роль: EXTRACT | Серьёзность: Средняя | Уверенность: подтверждено чтением кода
Где: `app/tool/http_fetch.py:59` (`MAX_BYTES`), `:419-420` («Слишком большой файл, не читаю»)
Простыми словами: крупная статистическая выгрузка (>40 МБ) просто пропускается целиком.
Суть: при превышении — отказ без попытки скачать частично или считать потоково.
Последствия: недобор крупных наборов данных (именно там часто самое ценное).
Исправление: для табличных типов сохранять на диск целиком (стримингом) даже >40 МБ и считать по нему кодом; предел применять только к загрузке в разговор.
Как проверить: фикстура >40МБ CSV — должна сохраниться на диск.

### [EXTRACT-08] robots/задержки не соблюдаются между вызовами `fetch` — риск блокировки IP владельца
Роль: EXTRACT | Серьёзность: Средняя | Уверенность: подтверждено чтением кода
Где: `app/tool/http_fetch.py` (`Fetch` — 8 параллельных запросов, без задержки; `Crawl` вежлив — `CRAWL_POLITE=0.3`)
Простыми словами: обычная загрузка бьёт по сайту без пауз и без учёта его правил; сайт может временно заблокировать ваш адрес, и тогда недоступным станет весь источник.
Суть: `Fetch.execute` — `asyncio.gather` до 8 адресов без задержки; повторные вызовы подряд не троттлятся. Это ведёт к 429/бану, то есть к недобору. (Юридическую сторону не рассматриваю — вне аудита.)
Последствия: временная потеря доступа к источнику из-за rate-limit.
Исправление: мягкий per-host троттлинг и для `fetch`; уважать `Retry-After` при 429.
Как проверить: счётчик запросов на хост в единицу времени.

### [EXTRACT-09] Определение JS-каркаса даёт ложноотрицательные на «тяжёлых» страницах с данными в скриптах
Роль: EXTRACT | Серьёзность: Средняя | Уверенность: подтверждено чтением кода
Где: `app/tool/http_fetch.py:697-706` (`_looks_script_built`: `len(body)<2500 И <5% от html`)
Простыми словами: страница, где важные данные рисует скрипт, но при этом много видимого меню/текста (>2500 знаков), не будет помечена как «нужен браузер» — агент прочитает меню и решит, что это и есть содержимое.
Суть: требуются оба условия (мало текста И малая доля). Страница с большим статическим обрамлением и данными в JS проходит как «полноценная».
Последствия: тихий недобор данных, отрисованных клиентом, на контентных порталах.
Исправление: дополнить эвристику признаками SPA (наличие `<div id="root">`/`__NEXT_DATA__`/большого объёма `<script>` при малом числе значимых блоков); при сомнении советовать `browser_exec`.
Как проверить: фикстура-SPA с крупным меню — должна помечаться.

## Требует разрешения
- Прогон конвейера на реальных «тяжёлых» порталах (госстатистика Армении/др.) с браузером — единственный способ измерить реальную долю успешной добычи. Нужны: сеть, браузер, возможно живая модель. Оценка: время + небольшие токены.
- Подключение OCR (tesseract) как эксперимент для EXTRACT-02 — установка пакета.

## Вне зоны
- Пересказ reader-моделью теряет «неважное» незаметно (роль 04/07) — рубеж после добычи.
- Инъекция со страницы (роль 01): агрессивный обход барьеров расширяет и добычу, и поверхность атаки.
